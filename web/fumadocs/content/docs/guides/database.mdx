## The idea

Paper persistence lives in an operator-provisioned MySQL 8 database or local
SQLite file. The plugin connects and checks that tables exist; it never creates them.

## basics

Apply the schema matching your chosen backend, configure its JDBC URL in
`database.yml`, then restart. Missing tables fail startup with a provisioning hint.

## Everyday

Sections targeting the same backend and JDBC URL share one Hikari pool. Keep MySQL
passwords out of git and back up either backend before changing live data.

## Advanced

<Callout type="info">Advanced — you do not need this to get started.</Callout>

Pool sizing, mixing backends by section, and the separate MySQL editor-session
service are operator concerns, not day-one work.

## Supported backends

The Paper plugin supports **MySQL 8** and **SQLite**. Use MySQL for shared or
multi-server deployments. Use SQLite for one standalone Paper server.
PostgreSQL, MariaDB, and MongoDB are unsupported. The separate `web/rest-api`
service remains MySQL-only.

## Schema ownership

| Store | Who creates tables? | Who only connects? |
| --- | --- | --- |
| **Paper / MySQL** | Operator / CI / script **once** | Paper plugin |
| **Paper / SQLite** | Operator / script **once** | Paper plugin |
| **Editor sessions / MySQL** | Operator / CI / script **once** | `web/rest-api` |

**Neither process ever runs DDL.** Provision every distinct database before
starting its consumer.

- MySQL schema: `modularjobs-paper/src/main/resources/sql/mysql.sql`
- SQLite schema: `modularjobs-paper/src/main/resources/sql/sqlite.sql`
- Missing schema objects cause startup to fail before repositories are used.

## Tables

| Table | Purpose |
| --- | --- |
| `job_progression` | Active player state: root job key, current node, tree XP |
| `archive_job_progression` | Archived player job state after leaving |
| `payable_records` | Task payables by job / action / context / type |
| `job_tasks` + `job_task_payables` | Task records with exact-decimal payables |
| `time_boost_identity` + `time_boosts` | Timed boosts (target, source, expiry) |
| `player_upgrades` | Skill points, unlocked nodes, node levels |
| `editor_sessions` | Secure editor payloads (MySQL REST authority only) |

MySQL stores durable money and XP amounts as `DECIMAL`. SQLite stores them as
decimal text so values round-trip without binary floating-point loss.

## Identical pools are shared

Pools with the same backend + `jdbc-url` + username share one HikariCP connection
pool, so pointing every section at one database costs a single pool:

```yaml
payable:
  type: mysql
  jdbc-url: jdbc:mysql://127.0.0.1:3306/modularjobs
  username: modularjobs
  password: change-me
  maximum-pool-size: 10
```

## Provision MySQL 8

```bash
# Local / CI
export DATABASE_URL=mysql://user:pass@host:3306/modularjobs
./scripts/apply-mysql-schema.sh

# Or, with the MySQL client configured for the target database
mysql --host=host --port=3306 --user=user --password modularjobs \
  < paper/src/main/resources/sql/mysql.sql
```

For local development, run MySQL 8 externally and apply the schema before
starting its consumer.

## Provision SQLite

```bash
./scripts/apply-sqlite-schema.sh \
  /absolute/path/to/plugins/ModularJobs/modularjobs.db
```

Point each Paper persistence section at the provisioned file:

```yaml
payable:
  type: sqlite
  jdbc-url: jdbc:sqlite:plugins/ModularJobs/modularjobs.db

timed-boost:
  type: sqlite
  jdbc-url: jdbc:sqlite:plugins/ModularJobs/modularjobs.db

progression:
  type: sqlite
  jdbc-url: jdbc:sqlite:plugins/ModularJobs/modularjobs.db

upgrades:
  type: sqlite
  jdbc-url: jdbc:sqlite:plugins/ModularJobs/modularjobs.db
```

SQLite needs no username or password and always uses one pooled connection.
Every distinct target receives the complete matching schema.

## Startup behavior

1. Open or reuse each configured Hikari pool.
2. Verify required tables exist (`job_progression`, `job_tasks`, …).
3. Verify migration-sensitive columns, including `current_node_key`, exist.
4. Missing tables or columns → **fail enable** with the matching schema or
   migration instructions.

## Task data ownership

The plugin does not seed `job_tasks`. An empty task table remains empty until an
operator creates definitions through the editor/repository path or reviewed SQL.

<Callout type="warn" title="Live task changes">
The selected `payable` backend is the runtime source of task data. Back up live
rows before bulk edits or deletes. The `fisher` → `fisherman` job-key rename
likewise requires an operator-managed data update before deploying the renamed catalog.
</Callout>

## What it means for you

Choose SQLite when the database belongs to one Paper server and low setup overhead
matters. Choose MySQL when data must be shared, remotely administered, or consumed
by the editor-session API. In both cases, provision and back up the schema yourself.
